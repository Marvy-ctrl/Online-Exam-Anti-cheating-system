PART 2: POTENTIAL EXAMINER QUESTIONS & WINNING ANSWERS
=============================================================================

Q1: Why did you choose to use Celery and Redis for face verification instead of just doing it directly in the backend?
A: Face recognition (running HOG and ResNet-34) is very CPU-intensive. It takes about 850ms to process one frame. If I did this directly in the FastAPI route, the web server would freeze, and other students wouldn't be able to submit their answers or load pages. By pushing the image to a Redis queue and having a background Celery worker process it, FastAPI immediately responds to the student in 18ms, keeping the exam smooth and lag-free while the heavy lifting happens in the background.

Q2: How do you handle network failures or power outages during the exam?
A: The system relies on a continuous auto-save mechanism. Every time a student selects an option, it triggers an HTTP request. If the network drops, the frontend initiates a "3-retry loop". If all retries fail, it alerts the student. If their PC goes off, their session state (time remaining, saved answers) is securely preserved in the PostgreSQL database, so they can log back in and resume exactly where they left off without losing any data.

Q3: Why did you set the Euclidean distance threshold to 0.40?
A: 0.40 is the optimal mathematical tradeoff. If I made it stricter (e.g., 0.30), the system would throw false alarms just because the student tilted their head or the lighting changed (15% False Rejection Rate). If I made it more lenient (e.g., 0.50), it would allow people with similar facial structures to cheat (4% False Acceptance Rate). 0.40 provides maximum security (0.08% FAR) with minimal disruption to honest students.

Q4: What happens if the student changes their computer's clock to buy more time?
A: The countdown timer on the frontend is purely visual. Security is "Server-Authoritative". When the exam starts, the backend calculates the exact 'expected_end_time' and locks it in the database. When the student submits answers, the server checks the current server time against the database deadline. If the time has passed, the submission is rejected, making client-side time tampering impossible.

Q5: Are there privacy concerns with storing students' faces?
A: Yes, which is why the system was designed with "Biometric Minimization" and GDPR compliance in mind. Raw images of students are not saved to the hard drive during normal face checks—they are processed in memory and discarded if there is a match. An image is ONLY permanently saved to the MinIO object storage if a violation (like cheating or a face mismatch) is flagged, serving as audit evidence. Furthermore, an automated lifecycle policy deletes all snapshots after 7 days.

Q6: How does the system prevent a student from just covering their webcam?
A: If the webcam is covered or blocked, the HOG face detector will return zero localized faces. The system flags this as a "Face Absence" violation and immediately logs it in the database while sending a real-time WebSocket alert to the examiner's dashboard.

Q7: What is the limitation of your system?
A: A primary limitation is the reliance on decent lighting and network bandwidth to send webcam snapshots. Also, while it tracks faces, it doesn't currently track eye-gaze (where exactly the student is looking on the screen). Adding WebGL-based gaze tracking and WebRTC for live video streaming are recommendations I've included for future work.
