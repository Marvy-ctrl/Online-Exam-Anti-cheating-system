This study adopts a design and implementation-based methodology, focusing on the development and evaluation of an E-Examination Cheating Control System (ExamLoc). The methodology involves requirement analysis, system design, component implementation (programming), testing, and integration under real examination-like scenarios. 

To bridge the gap between initial design and final implementation, the methodology incorporates both client-side tracking and an asynchronous, server-side biometric verification pipeline to support a scalable, secure, and user-responsive digital exam environment.

3.1 Research Design and Architecture

3.1.1 System Overview
This system introduces an approach that tackles cheating in online examinations through the development of a real-time e-examination monitoring and biometric verification system. This setup is built around a hybrid synchronous/asynchronous architecture that monitors students' activities during examinations, helping to identify suspicious behaviors and verify physical identity.

The system functions by tracking candidate actions in the browser and capturing periodic webcam frames, transmitting them to the backend in real time. FastAPI serves as the backend routing core, facilitating database transactions, user session states, and client endpoints. To support live monitoring updates, the system utilizes WebSockets, streaming behavioral violations directly to examiner dashboards.

Crucially, to prevent server performance degradation under heavy computational load, the system separates browser-level event analysis from face recognition. While browser focus and right-click actions are checked using deterministic frontend and backend rule-based logic, face verification is offloaded to an asynchronous task queue. The backend leverages a biometric pipeline containing grayscale quality checks (evaluating luminance and sharpness), face localization (HOG detector), and a pre-trained ResNet-34 neural network to extract 128-dimensional facial vectors. These vectors are verified against the student’s enrolled template using Euclidean distance comparisons.

Separating the exam interface from heavy biometric processing keeps the system fast and prevents any lag or interruptions for the student.

Events generated from the student’s device are transmitted via REST endpoints or a persistent WebSocket connection. While simple event data and answers are written directly to PostgreSQL, biometric snapshots and heavy calculations are queued through Redis to Celery background workers. The results are logged, and live violation alerts are broadcast back to the examiner dashboard.

The system consists of four main architectural tiers:
1. **Client-Side Monitoring Agent (Next.js)**: Operates within the candidate’s web browser during an active exam. It renders exam content, captures behavioral events (tab switches, focus loss), blocks unauthorized inputs (right-clicks, copy actions), and grabs periodic webcam frames.
2. **Server-Side Application Layer (FastAPI)**: Serves as the core logic layer. It manages authentication, controls session timelines, receives monitoring streams, and writes metadata to the database.
3. **Asynchronous Processing Layer (Celery & Redis)**: Handles CPU-heavy transactions. It processes incoming webcam snapshots, runs quality checks, extracts face embeddings, performs biometric matches, and executes MCQ autograding tasks.
4. **Data & Storage Layer (PostgreSQL & MinIO)**: Persists metadata (users, exams, logs) in PostgreSQL using SQLModel, and stores physical audit snapshots in MinIO object storage with an automated 7-day lifecycle deletion policy.

3.1.3 Explanation of System Components
The proposed system is structured as a multi-component architecture. Each component performs a specific role and collaborates to ensure continuous supervision during examination sessions:

1. **Student Interface (Next.js Client)**:
   Runs directly in the browser to deliver exam content and monitor student behavior. It tracks tab switching, captures focus loss events, and blocks input actions (such as copy, paste, and text selection). Answers are synced back incrementally via a fault-tolerant auto-save request loop.

2. **Biometric Pipeline (face_recognition / dlib)**:
   Executes image quality validation and face verification workflows. It enforces a grayscale quality gate to check image brightness and contrast before running a pre-trained ResNet-34 neural model. The model computes 128-dimensional biometric embeddings and compares face similarity via Euclidean distance math.

3. **Asynchronous Task Queue (Celery & Redis)**:
   Buffers and offloads heavy background operations from the web gateway. The FastAPI router pushes time-consuming face evaluations and MCQ auto-grading tasks to the Redis queue, allowing the Celery workers to process them asynchronously without freezing the user interface.

4. **Real-Time Communication Hub (WebSocket & Redis Pub/Sub)**:
   Facilitates low-latency messaging. It keeps a persistent connection open between active browsers and the server. When behavioral anomalies are flagged, the backend publishes the violations to a Redis Pub/Sub channel, broadcasting alerts immediately to supervising examiners.

5. **Persistence Layer (PostgreSQL & SQLModel)**:
   Manages core relational data storage. Using SQLModel as the database mapping framework, it stores user roles, configurations, exam templates, and event records, relying on indexing and unique composite constraints to secure multi-tenant access.

6. **Secure Object Storage System (MinIO & Local Fallback)**:
   Hosts and protects proctoring snapshot records. Suspicious base64 frames are converted to binaries and stored using obfuscated UUID paths. If the storage service goes offline, files write to local directories automatically, proxied behind strict backend auth checks.

7. **Examiner Dashboard (Next.js Proctor)**:
   Provides a central workspace for administrators. It updates in real time to show active candidates, live webcam thumbnails, aggregated violation alerts, and timeline streams for proactive exam supervision.

3.1.5 System Process and Interaction Design
To capture the dynamic relationships between the user interfaces, the API gateway, the task worker queue, and the proctoring monitor, the system is designed around two critical interaction sequences:

1. **Pre-Exam Biometric Verification & Exam Entry Sequence**:
   Before the student can view examination questions, their identity must be verified against their enrolled biometric template. The client captures a live webcam frame and submits it to the backend. The backend matches the 128-dimensional embedding, generates a time-bound session key, and initializes the countdown.

2. **Periodic Asynchronous Proctoring & Alert Sequence**:
   During the exam, behavioral and biometric telemetry are sent continuously. While browser events (visibility changes) trigger instant WebSocket broadcasts to the examiner, webcam snapshots are routed through a background worker to avoid UI freezes.

3.2 Real-Time Event Monitoring and Handling

3.2.1 Types of Events Captured
During an exam, the client-side monitoring agent and server-side worker continuously observe and capture specific indicators:
- **Browser Tab Switching**: Triggers when visibility API reports the page is hidden.
- **Window Focus Loss (Blur)**: Triggers when the active browser focus shifts to another app.
- **Webcam Availability (Face Absence)**: Captures if the video stream cuts out or if no face is localized.
- **Multiple Face Presence**: Captures if the localized face count exceeds one.
- **Biometric Identity Mismatch**: Flags if the Euclidean distance between the live capture and reference template is 0.40 or higher.
- **Clipboard/Right-Click Violations**: Intercepts copy-paste actions and context menu clicks.
- **Network Interruptions**: Triggers when WebSocket heartbeats are missed.

3.2.2 Event Transmission and Asynchronous Offloading
To ensure consistent monitoring without affecting client browser performance or server responsiveness, the system uses two main transmission strategies:
- **Immediate Behavioral Events**: Simple events (tab switches, focus loss) are sent as HTTP POST requests with `keepalive: true` configured. This forces the browser to complete the network request even if the tab is immediately shut down. Simultaneously, these events are sent over the active WebSocket channel for live monitor broadcasts.
- **Heavy Biometric Checkloads**: Base64-encoded webcam snapshots are posted every 20 seconds. Instead of making the client wait for image decoding and vector comparison, the FastAPI router serializes the payload, pushes it onto the Redis task queue, and returns an immediate response (HTTP 200 "queued"). The Celery background workers dequeue the task and run the biometric inference asynchronously.

3.2.3 Rule-Based and Biometric Event Evaluation
Once an event reaches the server, it is directed to the appropriate evaluation handler:
- **Rule-Based Evaluation (Behavioral & Biometric Status)**: Employs a continuous logging policy with zero baseline tolerance. The system does not ignore minor or initial occurrences; instead, every single event—including the very first instance of a tab switch, window focus loss, face absence, or multiple faces detection—is logged immediately in the PostgreSQL database and streamed in real time to the examiner dashboard via WebSockets. The examiner's panel displays these cumulative violation logs as an audit timeline, allowing the human supervisor to review the full behavioral record of the candidate.
- **Biometric Matching Evaluation (Identity)**: Uses mathematical vector math. The system calculates the Euclidean distance ($d$) between the live embedding vector ($\vec{E}_{\text{live}}$) and the enrolled baseline template ($\vec{E}_{\text{enrolled}}$):
  $$d = \sqrt{\sum_{k=1}^{128} (E_{\text{enrolled}, k} - E_{\text{live}, k})^2}$$
  If the distance is below 0.40, the match passes. A distance of 0.40 or above indicates a biometric mismatch, raising a violation alert.

3.2.4 Event Logging and Violation Handling
When a violation is confirmed, the system:
1. Generates a unique log record containing the student's identifier, session ID, violation type, timestamp, and metadata.
2. Writes the record to PostgreSQL, updating the active session's running violation counter.
3. If a violation is flagged (e.g., face mismatch or tab switch), the worker writes the binary image payload to the MinIO storage bucket, linking the snapshot URL to the violation record.
4. Streams the violation alert immediately over WebSockets to the examiner dashboard via Redis Pub/Sub, updating the live examiner interface.

3.3 Tools, Frameworks, and Technologies

The system relies on a carefully selected tech stack to coordinate real-time tracking, biometric calculations, and secure data storage:

- **Backend: FastAPI (Python)**: Provides high-throughput asynchronous REST and WebSocket request handling.
- **Database ORM: SQLModel**: Combines SQLAlchemy and Pydantic, ensuring type-safe database queries and automated data validation schemas.
- **Database Engine: PostgreSQL**: Persists structured relational data, using indices (e.g., on student ID and exam ID) and composite unique constraints to guarantee multi-tenant security.
- **Task Broker & Queue: Redis & Celery**: Brokers tasks and runs background workers to handle CPU-bound biometrics and asynchronous grading computations.
- **Biometrics Pipeline: dlib & face_recognition**: Powers face localization and 128-d vector embedding extraction via a pre-trained ResNet-34 neural model.
- **Object Storage: MinIO (S3-Compatible)**: Handles raw image snapshots. Configured with a 7-day lifecycle deletion rule (`LifecycleConfig`) to automate GDPR storage limitation compliance.
- **Frontend: Next.js (React), TypeScript, & TailwindCSS**: Renders the candidate exam environment, intercepts input controls, and powers the examiner proctoring dashboard.
- **Testing Tools: Pytest & Restfox**: Pytest executes the automated testing matrix (12 core test cases, TC-01 to TC-12) to verify security and fault tolerance, while Restfox verifies endpoint functionality.

3.4 System Workflow

The system workflow illustrates the step-by-step operation of the proposed online examination monitoring system:

1. **Administrator Pre-Enrollment**: The examiner registers student credentials (ID, email) inside the admin panel, generating a tokenized, single-use enrollment link.
2. **Biometric Student Enrollment**: 
   - The student opens the enrollment link.
   - The frontend captures 5 webcam photos.
   - The backend runs luminance and sharpness checks. 
   - Passing embeddings are averaged element-wise ($\vec{E}_{\text{enrolled}} = \frac{1}{M} \sum \vec{E}_j$) and saved as the baseline reference template, changing student status to `enrolled`.
3. **Exam Session Verification Gate**: On exam start, the student logins. The system captures a live webcam frame, checks quality, and verifies it against the reference template. If Euclidean distance < 0.40, a JWT cookie (`exam_auth_token`) is issued, and the student enters the exam hall. The server locks the session's `expected_end_time`.
4. **Active Exam & Event Tracking**: As the candidate answers questions, their selections are sent via an auto-save loop with a 3-retry network fallback. Simultaneously, browser visibility and blur focus listeners capture any tab switching or navigation actions, posting them to the violation endpoint immediately.
5. **Periodic Facial Checks**: Every 20 seconds, the client sends a live frame snapshot. FastAPI forwards this to Celery asynchronously. If a violation is found (mismatch, multiple faces, face absent), the snapshot is stored, and a violation entry is added to PostgreSQL.
6. **Real-Time Proctor Broadcast**: When a violation is written, the ConnectionManager broadcasts the alert via Redis Pub/Sub to examiner WebSockets, updating the live monitoring dashboard immediately.
7. **Exam Autograding & Reporting**: Upon submission or server-side deadline expiry, the Celery autograder scores the exam, persists the grade, and completes the session. Full violation summaries are exported for administrator auditing.
